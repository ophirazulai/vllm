An Optimization-Candidate Map and Literature Review vLLM V1 — locations primed for FunSearch / AlphaEvolve / OpenEvolve-style program search.

vLLM V1 is a re-architected serving engine (alpha released Jan 27, 2025; default since v0.8.x) organized around a multi-process design: an API server process, an EngineCore process running the scheduler + KV-cache manager, and one GPU worker process per device. Stable models, kernels, and distributed plumbing were inherited from V0; the new code that matters for evolutionary search lives almost exclusively under vllm/v1/, plus the still-shared vllm/model_executor/layers/ (kernels, MoE, quantization), vllm/attention/ops/ and vllm/compilation/.

The highest-ROI evolve targets cluster around four families: (1) heuristic decision logic with clear scalar rewards (scheduler, prefix-cache eviction, speculative-decoding draft policy, CUDA-graph dispatch); (2) Triton kernels with measurable latency (fused MoE, sampling, quantized GEMMs); (3) @triton.autotune / JSON-config search spaces (per-shape MoE configs); (4) numerical–performance trade-offs (KV-cache compression, FP8 quantization, hash choice).

Recommended First Targets

Ten highest-ROI evolve candidates, ordered by expected ROI (function isolation × clean fitness signal × literature headroom × maintenance risk).

  1. Fused-MoE Triton kernel autotune configs risk: low
    vllm/model_executor/layers/fused_moe/configs/*.json + fused_moe.py

    Per-(num_experts E, intermediate-size N, GPU device) JSON configs that select BLOCK_M / BLOCK_N / BLOCK_K / GROUP_M / num_warps / num_stages. Small structured space, hand-tuned grid misses optima. Evaluator: benchmarks/kernels/benchmark_moe.py. Literature gain: 1.5–2.5× over vendor defaults (GEAK-OpenEvolve, Kernel-Smith). → MoE module ↗

  2. Scheduler waiting-queue ordering policy risk: high
    vllm/v1/core/sched/scheduler.py :: Scheduler.schedule (line 352, file 2,295 LoC)

    Heuristic that selects which waiting request to admit next, the chunked-prefill chunk-sizing rule, the preemption victim selection, and the skipped_waiting re-queue logic (issue #27441). Evaluator: benchmarks/benchmark_serving.py on ShareGPT, Mooncake-Conversation, BurstGPT. AlphaEvolve precedent: discovered datacenter scheduler that recovered 0.7% of Google compute. → Scheduler module ↗

  3. Prefix-cache block-hash strategy risk: medium-high
    vllm/v1/core/kv_cache_utils.py + vllm/v1/core/block_pool.py

    Block-hash function chain (sha256 vs hash, multimodal extra-key mixing, parent-hash chaining order) and LRU/cached-block eviction priority. Correctness oracle: 1B-token collision tests. Literature: RadixAttention, Hydragen, ChunkAttention, MemServe/Mooncake. → KV-Cache module ↗

  4. Speculative-decoding draft-length / acceptance policy risk: low–medium
    vllm/v1/spec_decode/llm_base_proposer.py + ngram_proposer.py + dflash.py

    Per-request adaptive num_speculative_tokens, ngram prompt_lookup_min/max, EAGLE chain-vs-tree topology. Evaluator: examples/offline_inference/spec_decode.py on InstructCoder + MT-Bench. Wrong draft length only affects latency, never correctness. → Spec-Decode module ↗

  5. Top-k / top-p sampling kernel risk: low
    vllm/v1/sample/ops/topk_topp_sampler.py :: forward_cuda + apply_top_k_only

    Replacement of the forward_cuda top-k/top-p path (mixes sort, FlashInfer rejection-sampling, reduce). FlashInfer "sorting-free GPU sampling" blog (Mar 2025) suggests real headroom. Correctness via Kolmogorov-Smirnov. → Sampling module ↗

  6. Rejection-sampler Triton kernel risk: low
    vllm/v1/sample/rejection_sampler.py :: rejection_greedy_sample_kernel + expand_kernel

    Kernel block sizes, MAX_NUM_TOKENS unrolling, apply_sampling_constraints fused-vs-split strategy. Evaluator: spec-decode microbench. → Sampling module ↗

  7. CUDA-graph mode dispatcher risk: low
    vllm/compilation/cuda_graph.py + vllm/compilation/piecewise_backend.py

    Set of cudagraph_capture_sizes and FULL vs PIECEWISE vs FULL_AND_PIECEWISE selection rule per (model_size, attention_backend, batch_shape). Currently a static mode flag. Evaluator: vllm bench latency across {Llama-3-8B, 70B, Qwen3-30B-MoE, DeepSeek-V3} × {H100, B200}. → Compilation module ↗

  8. FlashInfer plan() / metadata-builder dispatch risk: medium
    vllm/v1/attention/backends/flashinfer.py :: FlashInferMetadataBuilder.build + plan()

    Cascade vs flat attention, prefill_fixed_split_size, disable_split_kv, TRTLLM-vs-FlashAttention dispatch on Blackwell. Currently a hand-coded if/elif lattice. → Attention module ↗

  9. Quantized GEMM auto-selection (Marlin / Machete / cuBLAS-FP8) risk: low
    vllm/model_executor/layers/quantization/utils/marlin_utils*.py

    Decision tree mapping (M, K, N, group_size, bit-width, dtype) → kernel implementation. Machete PR #7174 explicitly notes "Improve heuristic for 4096×4096" and "Improve batch size <32" as open work. Evaluator: benchmarks/kernels/benchmark_machete.py, benchmark_marlin.py. → Quantization module ↗

  10. Block-aligned chunked-prefill split for Mamba/hybrid risk: medium
    vllm/v1/core/sched/scheduler.py :: _mamba_block_aligned_split (line 302)

    Block-alignment policy for Mamba/hybrid models (Qwen3-Next, Jamba) — currently a hand-coded snap-to-block rule. Evolved rules can balance cache hit rate against unnecessarily small chunks. → Scheduler module ↗

Recommended Staged Plan

Stage 1 — Lowest-risk wins (week 1–2)

  • Start OpenEvolve on fused-MoE JSON configs (target #1) for one (E, N, GPU) tuple already used in production (DeepSeek-V3 / H100, Qwen3-MoE / B200). Benchmark already exists; falling back to configs/E=... is trivial.
  • In parallel, run OpenEvolve on top-k/top-p forward_cuda (target #5) using a microbench.
  • Threshold to escalate: ≥10% median latency improvement at iso-correctness.

Stage 2 — Medium-risk algorithmic targets (week 3–6)

  • Evolve the scheduler waiting-queue ordering (target #2) and spec-decode draft-length policy (target #4) inside a sandbox exposing only a restricted Python API (Request.priority, arrival_time, num_prompt_tokens, num_computed_tokens, kv_cache_utilization, running_lora_count, acceptance_history).
  • Threshold: Pareto-dominate the current FCFS+chunked-prefill baseline on (TTFT p99, TPOT p99, throughput) on ≥2 of 3 traces.

Stage 3 — High-risk / high-reward (month 2+)

  • Evolve prefix-cache hash function (target #3) and CUDA-graph mode/size dispatcher (target #7). Require strong correctness oracles: collision tests, full vLLM unit-test suite, lm_eval accuracy parity.
  • Evolve Marlin/Machete shape-dispatch heuristic (target #9) — likely highest dollar-impact target, sits in every quantized GEMM call in production.

Methodological notes

  • Use OpenEvolve with MAP-Elites archive keyed on (batch-size bucket, sequence-length bucket) — Kernel-Smith and KernelFoundry both report this is essential for kernel evolution.
  • Inject profiler feedback (NCU for kernels, Prometheus metrics for scheduler) — CUDA-L2 / CudaForge report ~2× sample-efficiency gain.
  • Always run a multi-trace evaluator; robust-kbench (Sakana 2025) shows single-input kernels often achieve illusory 50–120× speedups via benchmark exploits.
  • Co-evaluate accuracy preservation (lm-eval on a held-out set) for any candidate touching numerics.
  • Use vLLM's existing CI suite as a correctness gate before any candidate is committed.
Caveats. No experimental results in this report — this is a map, not a measurement study. Expected-gain numbers come from cited literature, not from running OpenEvolve on vLLM. The first concrete experiment (Stage 1, fused-MoE configs) is the cheapest way to ground these estimates. Several cited 2026 papers (Kernel-Smith, KernelFoundry, KernelEvolve, P-EAGLE, etc.) are still preprints — re-verify final venue/version. vLLM is mid-migration to MRV2 (vllm/v1/worker/gpu/); evolve targets should track MRV2 paths where possible to avoid bit-rot.
