Methodology How to actually run program-search on a vLLM target — staged plan, sandbox boundaries, and the meta-paper layer.

Per-module pages list where to evolve and the relevant domain literature. This page covers how — the program-search machinery itself (FunSearch, AlphaEvolve, OpenEvolve, Eureka, MAP-Elites), the recommended Stage 1/2/3 ramp, and the safeguards (correctness gates, multi-trace evaluators, robust-kbench-style benchmark hardening) that the cited literature considers mandatory.

Staged Plan

The recommended ramp from low-risk wins to high-risk / high-reward targets. Threshold-gated.

Stage 1 — Lowest-risk wins (week 1–2)

  • Start OpenEvolve on fused-MoE JSON configs (target #1, MoE module) for one (E, N, GPU) tuple already in production (DeepSeek-V3 / H100, Qwen3-MoE / B200). The benchmark benchmarks/kernels/benchmark_moe.py exists; falling back to the static configs/E=... on regression is trivial.
  • In parallel, run OpenEvolve on top-k/top-p forward_cuda (target #5, Sampling module) using a microbench. K-S correctness gate keeps this safe.
  • This pair gives one MoE-shaped and one sampler-shaped result quickly, on hardware similar to what evolutionary kernel papers (Kernel-Smith, KernelFoundry, GEAK-OpenEvolve) have already explored.
  • Threshold to escalate: ≥10% median latency improvement over the current configs/ baseline at iso-correctness, on a multi-trace evaluator.

Stage 2 — Medium-risk algorithmic targets (week 3–6)

  • Evolve the scheduler waiting-queue ordering (target #2) and spec-decode draft-length policy (target #4) inside a sandbox that exposes only a restricted Python API (Request.priority, arrival_time, num_prompt_tokens, num_computed_tokens, kv_cache_utilization, running_lora_count, acceptance_history). Use benchmarks/benchmark_serving.py against ShareGPT, Mooncake-Conversation, and BurstGPT.
  • Threshold: Pareto-dominate the current FCFS+chunked-prefill baseline on (TTFT p99, TPOT p99, throughput) on at least 2 of 3 traces.
  • Safety: add a fairness regression harness (cf. VTC, Locality-aware Fair Scheduling) before committing — easy to overfit to throughput at the cost of starvation.

Stage 3 — High-risk / high-reward (month 2+)

  • Evolve the prefix-cache hash function (target #3) and the CUDA-graph mode/size dispatcher (target #7). These need strong correctness oracles — collision tests on a 1B-token corpus + full vLLM unit-test suite + lm_eval accuracy parity. Use a 2-stage evaluator: (a) correctness gate, (b) performance scoring.
  • Evolve the Marlin/Machete shape-dispatch heuristic (target #9) — likely highest dollar-impact target because it sits in every quantized GEMM call in production.

Sandbox & Evaluator Recipe

Always do. Use OpenEvolve with MAP-Elites archive keyed on (batch-size bucket, sequence-length bucket). Inject profiler feedback into prompts (NCU for kernels, vLLM Prometheus metrics for scheduler). Run a multi-trace evaluator to prevent overfitting to a single workload. Co-evaluate accuracy preservation (lm-eval on a held-out set) for any candidate that touches numerics. Use vLLM's CI suite as a correctness gate before any candidate is committed.
Never trust loose tolerances. Kernel-Smith, EvoEngineer, and robust-kbench (Sakana AI 2025) explicitly document LLMs discovering "kernels" that pass loose tolerance tests but produce incorrect outputs in production. The Sakana paper documents that benchmark exploits inflated reported speedups by ~2× on KernelBench; treat all "12×–449×" headline numbers (CUDA-L1 v1) as upper bounds requiring robust-kbench-style validation.
C++ rebuild cost. vLLM-internal heuristics often live in C++/CUDA, not Python. Marlin/Machete kernel selection logic is partially inside CMake-built native code (csrc/quantization/); these are evolvable, but the evaluator harness must rebuild C++ on each candidate, multiplying iteration cost ~10–100×. Prefer the Python-side dispatch heuristics first.

Caveats & Anti-patterns

  • Don't trust headline numbers. The Sakana AI CUDA Engineer paper documents that benchmark exploits inflated reported speedups by ~2× on KernelBench. Treat all "12×–449×" claims as upper bounds requiring robust-kbench validation.
  • Don't skip the correctness gate. Kernel-Smith, EvoEngineer, and robust-kbench all document evolved kernels that pass loose tolerance but produce wrong outputs in production.
  • Don't overfit to one trace. Multi-trace evaluators (ShareGPT + Mooncake-Conversation + BurstGPT for serving; multi-shape grids for kernels) are mandatory.
  • Don't evolve C++ first. Iteration cost dominates; do Python-side dispatch heuristics first.
  • Track MRV2. vLLM is mid-migration to vllm/v1/worker/gpu/; evolved code targeting the legacy vllm/v1/worker/gpu_model_runner.py monolith risks bit-rot.
