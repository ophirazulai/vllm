1 Background — why this exists

vLLM offloads cold KV-cache blocks from GPU to CPU to extend usable context length and batch size. The eviction strategy directly controls hit rate, transfer volume, and tail latency — and there is no single best policy. It depends on workload shape, model, hardware, and request mix.

The problem

Different deployments want different policies (LRU, ARC, custom). Hand-tuning is slow and rarely reaches the optimum for a specific workload.

The opportunity

CORAL is an evolutionary search framework: an LLM proposes source-code mutations, a grader scores each candidate, the population improves over generations.

The bottleneck: spinning up a fresh vLLM engine per candidate is too slow — model load times dominate and mask the fitness signal CORAL is trying to optimise. The fix is to let CORAL swap a new policy into a running engine with zero restart.

2 CPU offloading — what gets swapped

vLLM's CPU offloading layer keeps a pool of CPU blocks that mirror evicted GPU KV-cache blocks. Whether a block is admitted, kept, or evicted is decided by a small CachePolicy object inside the scheduler-side CPUOffloadingManager. That single mutable pointer is the swap target.

The interface

Every policy implements five core operations plus state-transfer hooks and a constructor:

Read-side · safe to suppress

  • get(key) — content-addressed lookup; None means miss
  • touch(keys, ctx) — recency hint, advisory
  • evict(n, protected, ctx) — propose up to n victims; None means "couldn't free a slot this step"

Write-side · must succeed

  • insert(key, block, ctx) — admit a new block
  • remove(key) — manager-internal cleanup
  • export_state() / import_state() — swap-migration hooks

Built-in LRUCachePolicy and ARCCachePolicy implement the same ABC. Evolved policies subclass it and may consume the optional per-request req_context on insert/touch/evict. Class metadata (POLICY_NAME, POLICY_VERSION) is required for telemetry and reproducibility.

3 Hot-swap — replace policy in a live engine

A swap atomically replaces manager._policy while preserving in-flight requests, the CPU block pool, and resident block ownership. On any failure, the prior policy is restored before the lock is released — there is no half-applied state.

Three delivery modes

file path

Engine reads /abs/path/policy.py from its own filesystem.

dotted module

Resolves the source-backed .py file behind my_pkg.evolved_v3.

raw source

Source string sent over the wire — no filesystem dependency.

All three paths execute the source under a fresh synthetic module name (vllm._evolved.<hash>.<nonce>), so two loads of the same logical module produce distinct module objects with no shared globals. No importlib.reload, no overwriting user-controlled module names.

If any step from 1 onward fails, the rollback restores the prior manager._policy before releasing the lock. The canary runs on a brand-new empty policy — never on the migrated one — so a sentinel evict can never silently remove a real imported block.

Where the swap runs

The loader executes inside the engine process, not in the API server. Source/path/module is sent over IPC via the existing call_utility plumbing (the same pattern LoRA add/remove uses). Class objects are never pickled across the boundary.

Default-off, opt-in: the feature is disabled unless the operator passes --enable-policy-hotswap, sets enable_policy_hotswap=True in Python, or sets VLLM_ENABLE_POLICY_HOTSWAP=1. The HTTP route additionally requires a localhost client unless VLLM_POLICY_HOTSWAP_ALLOW_REMOTE=1. Source SHA-256 is logged on every load.

4 Per-request policy hints — co-evolving signal

Hot-swappable code is half the story. The other half is what the policy gets to look at. CORAL should be free to invent new request-level signal — priority, session id, expected reuse, tenant id, deadline — and have the evolved policy consume it at eviction time, all without changing vLLM's HTTP/Python schema across generations.

Carrier — reuse what's already there

Both CompletionRequest and ChatCompletionRequest already expose vllm_xargs as the documented user-extension field. We pick the sub-key policy_hints and treat it as opaque dict[str, Any] end-to-end. No HTTP schema change is required.

Design choices

Additive & default-None

Built-in LRU/ARC accept and ignore req_context. Operators not running hot-swap pay nothing. Evolved policies opt in only where they need it.

Reserved _request_id

The carrier injects a stable per-request handle so policies don't have to invent one. Names starting with _ are framework-reserved.

Cross-request merge is policy-defined

OffloadKey is content-addressed: request A inserts, request B touches. Each call gets the caller's hints; the policy decides the merge convention (last-wins, weighted, custom).

Untrusted user input

Hints come from any HTTP client. Framework guarantees only that hints are None or a dict. Evolved policies must validate shape, types, and sizes themselves — no eval, no path traversal, no PII echoing.

Telemetry — hint_keys

The manager unions the top-level keys seen in policy_hints per stats window (values are deliberately not exported — keys leak less than values). The grader uses this as a smoke signal that its client shim's hints actually propagated.

5 Safety net — surviving buggy policies

CORAL will produce candidates that pass the swap-time canary but misbehave under load. The engine cannot crash on these — every crash forces a fresh LLM, defeating the point of hot-swap. A layered defence wraps every evolved policy (built-ins are not wrapped and pay no overhead).

SupervisedCachePolicy

Inline wrapper installed at swap time. Read-side exceptions (get, evict, touch) become safe defaults — degraded gets become misses, degraded evicts mean "couldn't free a slot this step".

Error budget & trip

Each suppressed exception increments an error counter. When the budget is exhausted the supervisor trips and signals for rollback at the next safe point.

Cold auto-rollback

At a quiescent point (next external swap, or via EngineCore's idle callback) the registry recovers into a fresh LRUCachePolicy populated from the failed policy's exported residents. Block pool is reconciled — no leaked CPU slots.

Manager hardening

prepare_store allocates blocks then calls _policy.insert in a loop. The hardened version unwinds successful inserts and frees their blocks if a later insert raises, then returns None instead of crashing — the offloading connector retries on the next step. Worth landing on its own merit, since even built-in policies could in principle raise (e.g. OOM during dict resize).

Stats expose the protection signal

Snapshots include policy_errors, policy_rolled_back, and rollback_generation. These are sticky-within-window: the grader can call get_offload_policy_stats() after a candidate finishes and still see whether its score came from the candidate or from the recovered baseline.

What it does not protect against: a policy that calls os._exit(), mutates manager.__dict__ directly, or hangs in an infinite evict() loop. The supervisor is a robustness layer, not a security boundary — the default-off / localhost-only gating from §3 is what guards against running untrusted code in the first place.

6 API reference

Three layers of API stack on top of each other. The runtime API (OffloadingManager) is what the offloading connector calls every scheduler step to look up, load, store, and evict KV blocks. The policy API (CachePolicy) is the seam an evolved policy plugs into — every runtime call ultimately fans out to one or more policy methods. The control plane (HTTP + Python) lets an outside actor (CORAL grader, operator, test) swap the active policy and read stats without touching the running engine.

How the layers connect. A request flows scheduler → connector → manager → policy → block pool. The manager owns the block pool and ref-counting; the policy owns the index and the eviction decision. Hot-swap replaces the policy pointer between scheduler steps; the manager and block pool are unchanged.

6.1 Runtime API — OffloadingManager

Defined at vllm/v1/kv_offload/base.py. The CPU implementation lives at vllm/v1/kv_offload/cpu/manager.py. Every method runs on the scheduler thread; all state mutations are single-threaded by construction.

Two key types you will see throughout: OffloadKey is the content-addressed identifier for a block (a byte string packing a block hash + KV-cache-group index — see make_offload_key); BlockStatus is a ctypes.Structure holding (ref_cnt, block_id). ref_cnt = -1 means "not yet ready to read"; block_id indexes into the CPU buffer pool. ReqContext is a small dataclass with two fields: kv_transfer_params and policy_hints — both None unless populated from sampling_params.extra_args.

runtimelookup(key, req_context) -> bool

Is this block already offloaded and ready to read?

Inputs
  • key: OffloadKey — single block to check.
  • req_context: ReqContext — populated from the requesting Request; carries policy_hints.
Returns
  • True if _policy.get(key) returns a BlockStatus whose ref_cnt >= 0 (the block has finished its complete_store).
  • False if the block is missing or still in-flight.
  • The ABC permits returning None to mean "retry later"; the CPU implementation never does so.
Side effects
  • Increments _stat_lookups, and _stat_hits on a hit.
  • Adds the top-level keys of req_context.policy_hints to _stat_hint_keys (telemetry only — values are not exported).
runtimeprepare_load(keys, req_context) -> LoadStoreSpec

Pin a set of resident blocks so they cannot be evicted while a worker reads them.

Behavior
  • For every key, asserts the block is resident and ready, then increments BlockStatus.ref_cnt by 1. The block stays pinned until a matching complete_load call arrives.
  • Returns a CPULoadStoreSpec wrapping the block IDs that the worker side will use to issue the actual D2H/H2D copy.
Errors
  • Asserts on a missing key or a not-ready block — the caller is expected to gate this on a prior lookup. A buggy policy that returns None for a key the manager believes is resident trips this assert; that is the intended loud-failure path (§5).
runtimetouch(keys, req_context) -> None

Recency hint for blocks that did not need a read (e.g. served from the GPU prefix cache).

Behavior
  • Forwards directly to _policy.touch(keys, req_context). The base implementation on OffloadingManager is a no-op; the CPU subclass forwards.
  • Advisory only — suppressing it costs only recency information.
  • Called from OffloadingConnectorScheduler._touch at both the full-attention and sliding-window branches; the scheduler always has req_status.req_context in scope.
runtimecomplete_load(keys) -> None

Match for an earlier prepare_load: decrement ref_cnt on each block.

Notes
  • Asserts ref_cnt > 0 on entry. If a buggy policy lost the block between the prepare and the complete, this assert is the loud failure that triggers SupervisedCachePolicy rollback.
  • Context-free — no req_context parameter; by the time the load completes, the original request may already have moved on.
runtimeprepare_store(keys, req_context) -> PrepareStoreOutput | None

Make room for and admit new blocks. The hot path of the offloading connector.

Algorithm
  1. Filter out keys already resident — those don't need re-store.
  2. If the remaining set exceeds free capacity, call _policy.evict(num, protected, req_context) with protected = set(keys). None from the policy means "couldn't satisfy this step" and propagates up as None; the connector retries next step.
  3. Validate the policy's eviction output structurally: list type, length, no duplicate keys / block IDs, no protected keys, every block in range, every block ref_cnt == 0, post-evict get returns None. Malformed output → log + record_write_error + return None.
  4. Allocate the block pool slots, then loop _policy.insert(key, block, req_context). Hardened insert loop (§5): if any insert raises, undo all prior inserts (best-effort remove), free every allocated block, call record_write_error, return None instead of crashing.
  5. Build a CPULoadStoreSpec with the new block IDs and return it inside PrepareStoreOutput alongside the list of evicted keys (consumed by the connector for downstream KV-event emission).
runtimecomplete_store(keys, success=True) -> None

Finalize a previously prepared store. On success=True the block becomes loadable; on success=False the block is reclaimed.

Behavior
  • success=True → set ref_cnt = 0 on each not-yet-ready block, emit an OffloadingEvent(removed=False).
  • success=False → call _policy.remove(key) (best-effort; exceptions are caught and routed to record_write_error), then free the block. The engine survives a buggy remove.
  • Already-resident keys (those whose get returns None or whose block is already ready) are silently skipped — handles races with parallel stores cleanly.
runtimetake_events() -> Iterable[OffloadingEvent]

Drain the event buffer (only populated when enable_events=True). Used by KV-event emitters that publish offload activity downstream.

runtimetake_policy_stats(reset, active_generation) -> dict

Snapshot of manager-owned counters consumed by the registry's stats API. Returns a plain dict so the registry composes it with supervisor / sticky-rollback fields without circular import.

Fields
  • lookups, hits, stores, evictions, loads — counters since last reset.
  • hit_rate — hits / max(lookups, 1).
  • window_start_generation, active_generation — let the grader detect that a window spans multiple policies.
  • hint_keys — sorted tuple of top-level hint keys observed since last reset.
Reset semantics
  • reset=True zeroes counters and bumps window_start_generation to the current active_generation; clears hint_keys. The CORAL grader calls this at the start of each candidate's run.

6.2 Policy API — CachePolicy

Defined at vllm/v1/kv_offload/cpu/policies/base.py. Every evolved policy subclasses this ABC. Built-ins LRUCachePolicy and ARCCachePolicy are reference implementations.

An evolved policy looks like this:

from collections.abc import Iterable
from vllm.v1.kv_offload.base import OffloadKey, ReqContext
from vllm.v1.kv_offload.cpu.policies.base import BlockStatus, CachePolicy

class MyPolicy(CachePolicy):
    POLICY_NAME = "tournament-arc"
    POLICY_VERSION = "v3"

    def __init__(self, cache_capacity: int, **kwargs):
        self._cap = cache_capacity
        self._table: dict[OffloadKey, BlockStatus] = {}
        # ... custom data structures ...

    def get(self, key):
        return self._table.get(key)

    def insert(self, key, block, req_context=None):
        priority = (req_context.policy_hints or {}).get("priority", "normal") \
            if req_context else "normal"
        # ... policy-specific bookkeeping ...
        self._table[key] = block

    def remove(self, key):
        self._table.pop(key, None)

    def touch(self, keys, req_context=None):
        # ... bump recency ...
        pass

    def evict(self, n, protected, req_context=None):
        candidates = [k for k in self._table if k not in protected]
        if len(candidates) < n:
            return None
        victims = self._pick(candidates, n, req_context)
        return [(k, self._table.pop(k)) for k in victims]

    def export_state(self):
        for key, block in self._table.items():
            yield key, block
policy__init__(cache_capacity: int, **kwargs)

Construct an empty policy sized for cache_capacity CPU block slots. The widened signature lets the swap request pass policy_kwargs through; built-ins ignore extra kwargs.

Class-level metadata (POLICY_NAME, POLICY_VERSION) is read by the registry for telemetry and reproducibility — required to be non-empty before the pointer flip (the request body's name/version can override them).

policyget(key) -> BlockStatus | None

Content-addressed lookup. None means "not in cache" — including not-yet-stored. Context-free because get may run outside any request scope (e.g., supervisor cold-rollback validation).

Read-side. Wrapped by SupervisedCachePolicy: exceptions are converted to None (a forced miss) and increment the error budget.

policyinsert(key, block, req_context=None) -> None

Admit a freshly allocated BlockStatus under key. Called from prepare_store after the manager has reserved a CPU slot. The block will be in the not-ready state (ref_cnt = -1) until a matching complete_store arrives.

Hint usage
  • If req_context is non-None, req_context.policy_hints is the per-request opaque dict (or None). Read keys you care about; tolerate missing keys.
  • Do not mutate the dict — multiple touch/evict callers may see it.

Write-side. Exceptions propagate to the manager's hardened loop, which unwinds and frees blocks. SupervisedCachePolicy does not swallow write-side exceptions; instead the manager calls record_write_error.

policyremove(key) -> None

Manager-internal cleanup. Called from complete_store(success=False) and from the hardened-loop rollback path. No request scope.

Idempotent removal is safest; complete_store calls remove best-effort and continues regardless of exceptions.

policytouch(keys, req_context=None) -> None

Bump recency for an iterable of keys. The default contract is "advisory" — the manager continues if this raises (read-side suppression by SupervisedCachePolicy).

policyevict(n, protected, req_context=None) -> list[(key, block)] | None

Free exactly n slots, never touching keys in protected.

Contract
  • None means "cannot satisfy n evictions right now" — atomic: no state must change. The connector retries on the next step.
  • On success, return a list of (key, block) exactly n long, with no duplicates and no protected keys. The manager validates this structurally (§6.1 prepare_store); malformed output is treated as a write error.
  • Each returned block must have ref_cnt == 0 and a block_id in the allocated range.
  • Post-eviction, get(evict_key) must return None for each evicted key.

Read-side per the supervisor: exceptions become None. But malformed (non-None, structurally wrong) returns are treated as write errors.

policyexport_state() -> Iterable[(key, BlockStatus)]

Yield every currently resident (key, BlockStatus) exactly once. Called once on the outgoing policy at swap time; recency / ghost-list metadata is intentionally not exported.

Required: a swap aborts before touching manager._policy if the outgoing policy cannot export — dropping the index while the block pool stays allocated would leak CPU slots.

policyimport_state(items) -> None

Bulk-load resident blocks into a freshly constructed policy. Default implementation loops insert(key, block) with no req_context; subclasses may override for efficiency.

policyrecord_write_error() -> None

Notification hook called by the manager's hardened loop after a write-side exception or malformed evict output. The base implementation is a no-op so the manager never needs an isinstance check; SupervisedCachePolicy overrides it to advance the error budget.

6.3 Hot-swap HTTP API

Routes are registered from vllm/entrypoints/serve/policy_hotswap/api_router.py only when the feature gate is on (--enable-policy-hotswap, VLLM_ENABLE_POLICY_HOTSWAP=1, or enable_policy_hotswap=True). On a default deployment they do not exist.

Localhost by default. The router rejects non-loopback clients (anything not 127.0.0.1 / ::1) with HTTP 403 unless VLLM_POLICY_HOTSWAP_ALLOW_REMOTE=1. The gate is intentional: the swap endpoint executes arbitrary Python.
POST/v1/swap_offload_policy

Atomically replace the active CachePolicy on the engine's CPUOffloadingManager.

Request body
{
  "source_path":   "/abs/path/to/policy.py",   // exactly one of these three
  "module":        "my_pkg.evolved_v3",
  "source":        "class Policy(CachePolicy): ...",
  "name":          "arc-tournament",            // optional override of POLICY_NAME
  "version":       "v3",                        // optional override of POLICY_VERSION
  "policy_kwargs": {"target_t1_ratio": 0.5},    // forwarded to __init__
  "dry_run":       false                        // validate + canary, no pointer flip
}
  • Exactly one of source_path / module / source must be set; supplying zero or more than one is HTTP 400.
  • source_path resolves on the engine process's filesystem (not the API server's). Use source for containerized deployments where the path isn't visible.
  • module resolves a dotted name to its source-backed .py file, then loads it under a synthetic module name.
  • policy_kwargs is JSON-serializable kwargs passed to the policy's __init__.
  • dry_run=true runs the loader and the canary but does not flip the pointer or increment the generation; useful for CI smoke tests.

6.4 Hot-swap Python API

The same three operations are exposed symmetrically on LLM, LLMEngine, AsyncLLM, and AsyncLLMEngine. Async variants prefix with await; otherwise signatures are identical. 6.5 Per-request hints API

Hints are opaque per-request data the policy can consult at insert / touch / evict time. The carrier is the existing vllm_xargs field; the framework injects a reserved _request_id key but otherwise treats the dict as untrusted, untyped pass-through.

HTTPvllm_xargs.policy_hints

On POST /v1/completions or POST /v1/chat/completions:

{
  "model": "meta-llama/Llama-3.2-1B",
  "prompt": "...",
  "vllm_xargs": {
    "policy_hints": {
      "priority": "high",
      "session_id": "u-7732",
      "expected_reuse": 4
    }
  }
}

No HTTP schema change is required across CORAL generations — the hint dict is opaque end-to-end. vllm_xargs is a documented user-extension field already exposed by both completion request types.

PythonSamplingParams(extra_args={"policy_hints": {...}})

Offline / programmatic path:

llm.generate(
    prompts,
    [SamplingParams(max_tokens=256, extra_args={"policy_hints": h})
     for h in hints_per_prompt],
)

The carrier path: vllm_xargs.policy_hints → SamplingParams.extra_args["policy_hints"] → Request.policy_hints (validated via dict(raw_hints); _request_id injected) → ReqContext.policy_hints populated alongside kv_transfer_params in RequestOffloadState.__post_init__ → CPUOffloadingManager threads req_context into _policy.insert / touch / evict.

Untrusted user input. Hints come from any HTTP client. The framework guarantees only that policy_hints is None or a dict. Evolved policies must validate every key/value they consume — no eval, no path traversal, no PII echoing. Bounded-size dict.get with type checks; everything else is a policy bug.

7 Scope — what Phase 1 deliberately leaves out

Not in Phase 1

  • Weight-prefetch evolution — needs collective_rpc to workers and likely cudagraph re-capture. Sketched as Phase 2.
  • Sandboxing untrusted code. The threat model is documented; full isolation is out of scope.
  • Data-parallel broadcast / two-phase commit. data_parallel_size > 1 is rejected at engine init when hot-swap is enabled.
  • Hang protection. Operator-side wall-clock timeouts (the grader already kills runaway candidates).
  • Recency metadata across swaps. Only (key, BlockStatus) is migrated; evolved policies cold-start their LRU/ARC ordering.

What ships in Phase 1

  • Hot-swap of CachePolicy in CPUOffloadingManager, three delivery modes, atomic rollback.
  • Python (LLM.swap_offload_policy) and HTTP entry points; default-off + localhost-default.
  • Per-request policy_hints via vllm_xargs, end-to-end.
  • SupervisedCachePolicy, error budget, cold auto-rollback into a fresh LRU.
  • Stats surface (OffloadPolicyStats) and Prometheus metrics so the grader doesn't scrape logs.
